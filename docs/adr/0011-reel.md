# 0011: Reels

Status: accepted. The preview, the end card and the video export are implemented; which export
path each browser in CI takes has not been measured yet.

## Context

A diary is easier to share as a short, silent reel than as a folder of bursts. The reel must work
from the events already grouped for the diary, choose a bounded number of shots, and end on a card
that states what the diary contains without needing a server.

## Decision

`rankForReel(events, n = 8)` returns at most eight shots. Each burst contributes one shot: the
frame and species with the highest confidence, classifier score and visible box area, preferring
the species that the diary counts most independently. Bursts holding only the detector fallbacks,
blank frames, people or vehicles are left out. The selected shots are ordered by independent
detections, then frame quality, then camera time, so the first slide is the strongest evidence and
ties remain stable.

A shot lasts 1.2 seconds and the next shot crossfades in over 300 ms. The image drifts from 100%
to 104% over the shot; in the preview, `prefers-reduced-motion: reduce` removes both the drift and
the crossfade. The end card lasts 2.0 seconds, which gives 11.6 seconds for eight shots plus the
card and 9.6 seconds without it.

The end card lists the three species with the most independent detections, each count, the first
and last eligible camera dates, the project name and the package's `homepage` address. It reuses
the same independence interval as the diary and the CSV. Without a `homepage` the address is
absent rather than invented; the component also accepts an explicit address. No design direction
exists yet, so the card uses the preview's near-black background and white system type rather
than introducing a separate visual system.

The "Include end card" checkbox starts checked and stores the deliberate choice under
`deerdiary.reel.include-end-card` in local storage. Nothing is uploaded.

## Export

The export draws 1280 by 720 frames on a canvas at 30 frames a second, which divides a shot, the
crossfade and the card into whole frames: 348 frames with the card, 288 without. `reelLayers` in
`src/core/reel.ts` says what each frame shows; `src/app/reelExport.ts` draws and encodes it.

When `VideoEncoder.isConfigSupported({ codec: 'avc1.640028', width: 1280, height: 720 })` reports
support, mediabunny's `CanvasSource` encodes every frame with its own timestamp into an MP4. The
duration therefore comes from the frame count, not from timers. Otherwise `MediaRecorder` records
the canvas in real time, preferring VP9 WebM, then VP8, plain WebM, and last MP4 for a WebKit
recorder that writes only that. A recorded WebM has no duration in its header and runs past the
last drawn frame, so mediabunny rewrites the recording without re-encoding and cuts it at the
reel's length. A browser with neither path shows "Reel export is not supported in this browser."
where the button would be.

The exported file keeps the drift and crossfade even when the exporting browser asks for reduced
motion: the preference describes the person exporting, not whoever later watches the file.

Only the chosen shots are read. Their original `File`s come from the current drop, decoded one at
a time and scaled down to the size the drift needs. A session restored after a reload no longer
holds its originals, so its reel uses the stored thumbnails. mediabunny loads on the first export
and stays out of the start-up script; the service worker caches it then, so a browser that has
never exported while online cannot export offline.

## Verification

Unit tests cover the shot limit, one shot per burst, best-frame choice, fallback exclusion, the
independent-detection order, the top three end-card species, the two durations and frame counts,
the crossfade and drift of every layer, the encoder choice (including an engine that rejects the
H.264 configuration), the file name per container, and the exporter's states and messages.

`npx playwright test reel` mounts the reel with eight flat-colour photos and the real exporter,
exports with and without the card, and runs `ffprobe -v error -show_entries
format=duration:stream=codec_name` on each file: 11.6 and 9.6 seconds within 0.1 s, one video
stream, `h264` on Chromium and `h264`, `vp8` or `vp9` elsewhere. It grabs the frame at 10.6 s with
`ffmpeg -ss 10.6 -frames:v 1`, checks that it is the dark card rather than a bright shot, and
attaches the PNG for review. On a WebKit build with neither encoder it asserts the note instead.
It also drives the keyboard controls. The test records the codec each browser produced as an
annotation; this section should name the WebKit path once CI has run it.
